A LABEL COLUMN WITH A LANGUAGE TAG PRODUCED NO LABEL AT ALL

Found by running a real 26-sheet knowledge graph through the plugin instead of a fixture. The
first defect in this area where ROBOT raises nothing, produces axioms, and gets them wrong.

`A rdfs:label@en` is the obvious way to write an English label. Measured on robot-core 1.9.8 it
produces an annotation whose PROPERTY is

    http://www.w3.org/2000/01/rdf-schema#label@en

- the language tag concatenated onto the property IRI - carrying an untagged xsd:string. So
isLabel() is false and getLang() is empty: not a label in English, and not an rdfs:label at all.
The spelling that works is `AL rdfs:label@en`.

The asymmetry is the defect: ROBOT VALIDATES `AL` WITHOUT A TAG AND REJECTS IT, AND DOES NOT
VALIDATE `A` WITH ONE. Measured across every spelling:

    A rdfs:label                 0 problems   real rdfs:label, no tag
    A rdfs:label@en              0 problems   property rdfs:label@en, NOT a label
    AL rdfs:label                1 problem    correctly rejected by ROBOT
    AL rdfs:label@en             0 problems   real rdfs:label tagged en
    LABEL                        0 problems   real rdfs:label
    AT rdfs:label^^xsd:string    0 problems   real rdfs:label
    A rdfs:label@zz-nonsense     0 problems   property rdfs:label@zz-nonsense
    A rdfs:label@                0 problems   property rdfs:label@

Because the sheet succeeds in strict mode, none of the problem-placing machinery added in
1.106.0 is entered. The sheet is reported as perfect.

A NEW CLASS RATHER THAN A CONDITION

Nothing in this plugin had ever parsed the template row; the whole table was handed to
robot-core and whatever came back was the answer. That is why a column could be malformed in a
way that silently produced the wrong axiom.

TemplateColumns reads row two into typed columns - kind, property, language, datatype, SPLIT=,
and the `>` depth of an axiom annotation - and reports faults in the row itself. TemplateSheet
consults it before asking ROBOT anything, so faults arrive on the success path, which is the
only path this sheet takes. Threading them through mattered: one return path builds its own
problem list, and the faults would have been dropped there.

It refuses to report what it merely fails to recognise. ROBOT's acceptance pattern for
annotation columns is ^>{0,2}A[LTI]? .* and it gains column types between versions, so an
unknown spec parses to OTHER and is left alone. DOMAIN and RANGE were promoted out of OTHER
only because the MatWerk sheets use them - 2 of each, measured. One test asserts that fourteen
specs taken from real PMDco, ECTO and MatWerk templates produce no fault at all, because a
check that fires on a working sheet is worse than no check.

WHAT ELSE THE RUN ESTABLISHED, NOT ACTED ON HERE

Adding a row works end to end. Appending one organization - a fresh IRI, a type from the
sheet's own TYPE column, a label - and rebuilding every sheet gives +4 axioms and +1
individual, declared, typed OBI_0000245, two labels, and absent from the graph built before the
edit.

Reasoning over the whole graph does not finish. ELK on all 34,773 axioms: consistent, 0
unsatisfiable, 3.0 s. HermiT on the same: no result in 840 s, killed. The production pipeline
gates each sheet separately rather than the whole graph, and that is evidently the only shape
that terminates.

Cross-sheet label references are AMBIGUOUS rather than unresolvable, which corrects what the
1.106.0 work assumed. 57 institute labels are declared in two sheets; 55 agree on an IRI and 2
do not. "National Institute for Materials Science (NIMS)" has two distinct IRIs in scope and 9
of dataportal's 17 institute references name that label. A further 23 labels carry two IRIs
inside one upstream sheet alone. A reference resolves to whichever IRI ROBOT picks.
