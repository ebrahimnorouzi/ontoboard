rounds of corrections in this plugin - the catalog the build ignored, the release gate weaker than
CI, the reasoner accepting equivalences nobody asserted, a README documenting three of seven

The fixed point is the property that makes this safe to point at somebody's real project. A
generator that is not one rewrites files on every run, a user cannot tell a real change from noise,
and the first time they stop reading the diff is the time it deletes something.

THE BASE IRI DOES NOT COME FROM THE YAML

uribase is lossy: it writes only the part before the last slash, so
http://purl.obolibrary.org/obo/mwo.owl is recorded as http://purl.obolibrary.org/obo and the .owl
cannot be recovered. It is read from the edit file's xml:base instead - a file the regenerator must
not touch anyway. An extension-free IRI round-trips through uribase by luck, which is the kind of
accident that makes a bug look fixed; pizza's IRI is extension-free, so pizza would never have
caught this. The test uses one that would not.

WHAT IS NOT REGENERATED, AND ONE RECLASSIFICATION THAT MATTERED

Seven files. Five were obvious - the edit file, the custom Makefile, the YAML the regenerator reads,
the ID ranges (which carry every editor's allocation, not just this machine's account name), and the
catalog (which carries real import mappings the empty template would delete, breaking every robot
call in the build).

Two were not, and an analysis pass caught them after they had already been classified as
regenerable:

  profile.txt. The generated Makefile explicitly tells the user to edit it - "To relax one, change
  ERROR to WARN or INFO rather than deleting the line." Regenerating it would silently re-arm every
  rule a project had deliberately relaxed, and their next CI run would go red for something nobody
  changed. A test now pins that a relaxed rule survives an update.

  src/sparql/*.rq. The project's own quality checks. The scaffold writes check_labels.rq as a
  starting point; a project edits it and adds more, and sparql_test runs whatever it finds.

The four that remain all announce themselves as generated - the Makefile's first line is "WARNING:
generated by OntoBoard. Do NOT edit by hand." A user may still have edited the README or the
.gitignore, which is exactly why the action previews and writes nothing unless asked.

F9 IS SATISFIED

"One embedded ROBOT version, declared once." It was declared twice - pom.xml and a literal in
OdkScaffold - kept in step by a test. Now the pom has a single robot.version property; the
dependency takes it, and OdkScaffold reads it through a Maven-filtered ontoboard-build.properties.
The test pins both that the dependency uses the property and that filtering actually ran, because an
unfiltered build would put the literal placeholder into a generated CI file.

And the interaction that fix created, which had to be resolved rather than left to collide: once the
version came from the plugin's build, a regenerated qc.yml would depend on WHICH OntoBoard
regenerated it - moving a project's CI onto a different ROBOT than its curators report with, and
breaking the fixed point. So the version now belongs to the project: robot_version is seeded into
the YAML at creation and read back on regeneration. A project predating the key is reported rather
than silently given the plugin's.

Every ROBOT subcommand the generated Makefile invokes is reachable from a menu item: reason through
Transform, report through Quality report, verify through SPARQL, annotate through Release.

ALSO

Generated projects now ship a .gitattributes pinning eol=lf. Git is commonly configured with
core.autocrlf=true, so without it a Windows clone has CRLF in the working tree while the blobs are
LF - and then a byte comparison against regenerated content differs on that machine and nowhere
else. The regenerator additionally normalises line endings before comparing, never before writing.
