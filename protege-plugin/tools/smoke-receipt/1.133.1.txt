WHY THERE IS NO 1.133.0 RELEASE

1.133.0 was committed, pushed and tagged (v1.133.0, 5d1d9b3), and the release workflow failed in
its Test step - `mvn -B clean test`, run on the tagged commit before anything is packaged,
because the jar a user downloads has to be the jar that was tested. Nobody can download 1.133.0.
The tag stays, as v1.122.0's did.

Two failures, neither visible on the Mac 1.133.0's receipt was produced on, and neither said by
the run to anyone not signed in to GitHub, whose page showed "Process completed with exit code
1". The tests now print an annotation for each failure under GitHub Actions (GitHubAnnotations),
which is how both were found.

- Windows, failing on every push since d607d05: seven tests whose assertions passed, and then
  JUnit could not remove their temporary folders, because a Turtle file was still open. The OWL
  API leaves a handle on a file whenever it has to guess the format and a parser fails before
  one succeeds - measured with lsof: one handle on a Turtle file read by File or through an
  address mapped to it, none when the format is named or the file is RDF/XML. Windows will not
  delete, rename or replace an open file, so this held a user's file as well as a test's.
  OntologySource.loadFile now reads a file the way PatternIndex already did - through a stream it
  closes, under a stand-in document IRI - and OntologySource.load uses it for any address that
  resolves to a local file. OntologySourceTest counts the handles on Linux and macOS.

- Linux, intermittently since b2c386a: the second conversion of the same history wrote a
  different release file from the first - <terms:date rdf:datatype="...#string"> once and
  <terms:date> the next. "x" and "x"^^xsd:string are one literal, equal to the OWL API too, and
  its data factory, shared by every manager in a process, caches annotations and hands back
  whichever form it holds until a background eviction drops it. On a CI runner the cache
  sometimes cleared between the two conversions; on the Mac it never did. The conversion now
  writes every ontology with explicit xsd:string removed, so a converted repository is the same
  bytes whatever the cache did.

CI on ee27dad: the Test step passed on Linux and on Windows, and both Windows smoke runs passed.

  requirements..., Run self-test. ROBOT, Notes and Knowledge graph are gone as menus;
  Provenance... is Record who edits terms...; each entry is in one place.

FIXED

- A file OntoBoard read was held open on Windows until the garbage collector ran, when the OWL
  API had to guess its format - see above.
- A converted repository was not always the same bytes twice - see above.
- Opening an ontology left <file>.ontoboard.json beside it, and that file froze the outline:
  a board is now written from its first change only.
- A long row of pattern frames reached over the property sections, so lines from the outline into
  a pattern crossed them: the frames are folded into rows, and the sections start right of them.
- Messages and documentation pages named menu places that had moved, about 15 of them before the
  regrouping (ROBOT > Template..., Project > Pull request...). A test now follows every path,
  submenu by submenu, in the plugin's messages and on the pages.
- The build's report said "imported terms" for other ontologies' terms merged into the file.
- Run self-test left every view it built registered with Protege: it took the tabs it opened off
  the screen and never disposed them, so each run added listeners that stayed until Protege
  closed - 72 named when one workspace closed. The tabs are now closed as Protege's own close
  button closes one, and a tab check that fails names what was thrown.
- A jar could carry a class VS Code's Eclipse compiler had written for code javac rejects - its
  method replaced by a throw of "Unresolved compilation problem" - which Maven tested and packaged
  because it was newer than its source. The suite now fails on such a class (CompiledClassesTest),
  and this jar was built from a clean export of the commit.
