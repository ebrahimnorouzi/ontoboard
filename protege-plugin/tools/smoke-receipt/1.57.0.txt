THE TAB OPENS, AND THE CANVAS IS BUILT IN A HOST FOR THE FIRST TIME

  OntoBoard self-test item: Window > Tabs > OntoBoard | ok | opened, its views constructed, and
  closed again

F1 in the plan has nine clauses and this was the one never met: "opened the tab". It is met now, and
the same line retires something larger - the plan's list of what is "genuinely unverified" opens with
"whether the canvas paints", and SchemaCanvasView, 2,114 lines and the biggest class in the plugin, has
until now been exercised only by tests that construct no view.

Said exactly: this proves the tab opens and the views *construct*, on both hosts. It does not prove the
canvas *paints* - nothing here looks at a pixel, and the plan's unverified item is worded "whether the
canvas paints". Construction is the half where a missing OSGi import or a bad classfile version shows
up, which is the half worth automating; the rest still rests on somebody looking at it.

WHY IT WAS NEVER MET, WHICH IS NOT WHAT THE SCRIPT SAID

tools/smoke.ps1 looked for "Saved tab state for 'OntoBoard' tab". Protege logs that at *shutdown*, and
the smoke kills the process - so the line it waited for could never appear, whatever the tab did. The
script's header explained the absence differently: "Protege restores the last workspace, so the tab may
or may not open... asserting on the tab here would be asserting on the previous session's layout."

Half right, and the wrong half mattered. Measured on this machine: in a smoke run's log slice the tab is
not mentioned anywhere at all. It does not "may or may not" open - it never opens, because the self-test
runs from the editor-kit hook and nothing in that path asks for a tab. The condition was unmet for a
simpler reason than the script claimed, and the evidence it waited for was unobtainable either way.

So the self-test now asks. It finds the WorkspaceTab plugin Protege has registered, calls
addTabForPlugin, and removes the tab again - leaving the workspace as it found it, and short-circuiting
when a real user already has the tab open so that running the self-test from the menu cannot close it
underneath them.

TWO THINGS VERIFIED BEFORE BEING RELIED ON

The event thread. Every self-test line in the log is tagged [FelixDispatchQueue], so this runs on Felix's
dispatch queue and not the EDT. Constructing Swing components there is undefined rather than merely
impolite, and the failure it produces would have been blamed on the canvas. The check goes through
SwingUtilities.invokeAndWait.

The API, on both hosts. TabbedWorkspace was disassembled from protege-editor-core.jar in both installs
before a line was written against it: getOrderedPlugins, addTabForPlugin, containsTab and removeTab are
present and identical on 5.5.0 and 5.6.9. This project has been caught before by a Protege API that
differs between them, and "it compiles against one of them" is not the same claim.

A FALSE ACCUSATION, CAUGHT BY ITS OWN DIAGNOSTIC

The first version of this check looked the plugin up by the extension id in plugin.xml - OntoBoardTab -
and reported, when it found nothing:

  Protege lists no WorkspaceTab plugin with id OntoBoardTab, so the tab cannot be opened at all -
  plugin.xml and the bundle disagree, or the extension failed to load

That is a defect report about the plugin, and it was wrong. Protege composes a plugin's id from the
bundle and the extension, so the bare id from plugin.xml is not what getId() returns. The tab has always
worked for real users; the log's own history shows its state being saved.

The check now matches on the label as well - "OntoBoard", which is what Window > Tabs shows and is
closer to the thing being verified than an internal id - and, when nothing matches, prints every id and
label Protege did offer. A failure that names only what is missing gives nobody a way to find out why,
and this one would have sent somebody to audit plugin.xml for a bug that was in the lookup.

Worth recording plainly: the first output of this new check was a false accusation generated by my own
assumption. It took one iteration to find that out, and the fix was to make the check explain itself.

AND THE SUMMARY UNDERCOUNTED ITS OWN WORK

The run said "9 of 9 menu items ran" on a run that had checked ten things, because the tab is verified
outside the map the count is taken from. It now reads "10 of 10 checks ran - 9 menu items and the tab
itself." Small, and worth fixing because the receipts quote that line verbatim: a summary that
undercounts itself makes every other number in the file less believable.

HOUSEKEEPING THAT HAD BECOME A HAZARD

Since mvn clean stopped being usable here - the IDE's language server holds target open, so the clean
plugin fails on the directory itself - stale jars had been accumulating: 1.54.0, 1.55.0, 1.56.0 and
1.57.0 were all in target together. Nothing wrong shipped, because the install step names the version
explicitly, but that is exactly the arrangement in which somebody smokes a jar they did not build.
target/*.jar is now emptied as part of each build.

One consequence to read correctly: this build reports 1 skipped test rather than 0, because deleting the
jar before building means BundleConfigurationTest's jar-dependent case has nothing to inspect during the
test phase. The jar is built afterwards and is what both hosts loaded.
