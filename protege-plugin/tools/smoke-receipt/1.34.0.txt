EVERY MENU CLASS NOW LOADS AND CONSTRUCTS IN THE HOST

PluginXmlTest has called Class.forName on each of those 26 classes for a long time - on Maven's
classpath, where everything resolves. Felix is a different class space. A menu action that
references a Protege type this bundle never imported passes that test and throws
NoClassDefFoundError the moment a user clicks the item, and nothing anywhere would say so, because
a Protege action that fails to load simply does nothing visible. That is the same shape of defect
as the quality report, which sat broken for nine versions while every test stayed green.

Constructed, not merely loaded. Loading proves the class file is reachable; constructing runs the
static initialiser and the constructor, which is where a missing dependency actually surfaces.
Protege's actions are AbstractAction subclasses whose constructors do no work and open no windows,
so this costs milliseconds and has no side effects. initialise() is what Protege calls later and
this does not call it.

Be precise about what this is: it is half of what docs/superpowers' plan calls Phase 2. It can
tell you a menu item is dead. It cannot tell you its dialog is wrong, its parameters are
mislabelled, or its result is empty - nothing here clicks anything. Driving the actions is still
outstanding.

ALSO IN THIS RELEASE

ROBOT's axiom-level diff, as an opt-in beside the term-level comparison in
Project > Compare releases... They answer different questions and both are wanted: the term-level
table is what a release note is written from - which terms were added, obsoleted, redefined or
moved - and it exists because an axiom diff cannot answer that. A term that gained a definition
and a term that changed parents both look like "some axioms went, some came" to an axiom diff.
The axiom diff answers what exactly changed, which is the question when reviewing a release rather
than describing it. Labels are on, because a diff of forty axioms written as bare IRIs is one
nobody reads; ROBOT defaults them off.

DiffOperation was checked the way the last two ROBOT classes had to be: javap -v over the whole
constant pool, not a per-method disassembly. It contains no reference to RDF4J, openrdf or Apache
POI, which is why it can be called at all - ReportOperation and QueryOperation both turned out to
be unusable in a bundle for reasons no method signature revealed.
