THE OLDEST KNOWN DEFECT HERE IS FIXED

The starter template has never produced a single axiom. Measured again this week on five
projects - PMDco, NFDIcore, MWO, ECTO and a project OntoBoard scaffolds itself - every one
gave 0 axioms and 3 errors. It writes a CURIE taken from the last segment of the ontology
IRI, which is right for MWO and ECTO and wrong for the others, and it does not matter which:
no project declares that prefix and ROBOT's 277 built-in ones do not include it.

Against the real mwo-edit.owl: mwo:0000001 gives 0 axioms and 1 problem, MWO:0000001 the
same, the full IRI gives 4 and none. So the starter now writes full IRIs, taken from the
project's own -idranges.owl. All five projects:

    mwo        MWO_0030000      13 axioms   0 problems
    nfdicore   NFDI_0030000     13 axioms   0 problems
    pmdco      PMD_1000000      13 axioms   0 problems
    ecto       ECTO_9002179     13 axioms   0 problems

AND THE FIRST VERSION OF THAT FIX WOULD HAVE VANDALISED A PUBLISHED ONTOLOGY

Worth recording in full. The identifiers were first chosen as "one past the highest already
in the ontology", which is right when the ontology holds its own terms. nfdicore-edit.owl is
fifty-three lines that import components and contains ZERO NFDI_ identifiers. So the highest
came back as nought and the starter proposed NFDI_0000001 - which is a live published term,
"obsolete NFDI resource" - onto which the example row would have asserted
rdfs:label "an example term" and reported a clean success.

An id ranges file declares the blocks allocated to each editor, so one past the highest upper
bound is outside all of them by construction, whatever any single file happens to contain.
That is what it uses now, taking the larger of that and the signature. NFDI_0000001 became
NFDI_0030000.

The lesson is the one this repo keeps relearning: a rule that is right about the data in
front of you is not the same as a rule that is right.

OPENING A TEMPLATE IS NO LONGER A QUESTION

The sheet editor began with an empty grid and a file chooser, which puts a question to
somebody whose answer was already determined: a project has one place for its templates and
the editor knows where it is. SheetLocation works it out - src/templates beside src/ontology
for an ODK project, which is where ODK's own Makefile reads them and where PMDco and ECTO
both keep theirs, and a templates folder beside the ontology for anything else.

The view now opens them when it builds. Where there are none it says where they would go
rather than leaving somebody to guess. Nothing is created by looking: an editor that puts a
directory into a repository just by being opened is a surprise in the next git status.

New sheet... adds another template to the open folder with the same starter columns and the
same project identifiers, because a knowledge graph is many sheets - the one this was built
against is twenty-six - and adding the second should not mean leaving.
