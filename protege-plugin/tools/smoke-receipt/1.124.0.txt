WHY EACH IS THE SHAPE IT IS

  - DISJOINTNESS HAS NO DIRECTION, so no arrowhead at either end; an arrow would have a reader
    looking for one. Pairwise rather than through a hub, because an n-ary DisjointClasses means
    every pair is disjoint and a hub node would be a term the ontology does not contain. One line
    per pair in a fixed order, so an axiom stated from both sides does not draw two lines on top
    of each other.
  - A CHARACTERISTIC IS A FACT ABOUT ONE PROPERTY. Transitive has no second term for an arrow to
    reach, so an edge would misstate the arity. It rides on the property's label, where it is
    visible at a glance and costs no edges.
  - A CHAIN HAS THREE TERMS AND AN ORDER, so no two-ended shape fits. It reuses the node that
    already stands for "something the ontology says that is not a term" - the one anonymous class
    expressions get - with the links numbered so the order survives.
  - EVERY ONE OBEYS THE OPT-IN RULE: both ends must already be on the board. That is what stops
    disjointness from filling a taxonomy with red lines, and it is why the 38 inverse pairs appear
    only on a board where somebody has put the properties themselves.

AND ONE THING DELIBERATELY NOT DRAWN. SWRL rules - 4 on MWO. A rule is a horn clause over
variables; any node-and-edge shape for it would be an invented notation, and a picture that
misleads is worse than a gap that is written down. Protege's own rule tab shows them.


TERMS NO LONGER LAND ON TOP OF EACH OTHER

Reported: overlapping nodes. The cause was not the arrange algorithms - it was that
SchemaGraph.render placed every unpositioned node by a counter stepping right from (40,40) that
never looked at the stored positions. On a board anybody had arranged, the first saved node is
usually near the origin, so a newly added term went exactly on top of it. Worse, it is not a
once-per-term problem: every derived node the projection mints - a datatype, a class expression,
a property chain - arrives unpositioned on EVERY render.

CanvasPlacement.freeSlot searches a lattice for the first slot that touches nothing already
placed, claims it before the next node is asked for, and wraps after ten columns so thirty new
terms form a block instead of a line four thousand pixels long. Deterministic: the same board
gives the same arrangement every time, which matters because a render follows every edit
anywhere in Protege and a board that reshuffled itself would be unusable.

Six tests, including the one that matters - twenty-five nodes placed in sequence, every pair
checked for overlap.
