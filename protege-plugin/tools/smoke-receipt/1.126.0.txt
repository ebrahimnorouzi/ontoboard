A REFUSED COMMIT NOW SAYS WHAT THE DISAGREEMENT IS

docs/conflicts.md item 5 - "a read-only conflict report, best value per unit of work" - is done,
for git conflicts. Since 1.123.0 a commit on a conflicted tree has been refused, which stopped
the plugin recording conflict markers into an ontology and reporting success. What it left the
user with was a list of filenames and no way to find out what the two sides disagreed about,
because the one file they can open - the working copy - is the one version that is no longer an
ontology.

Both the refusal and "Show me what has changed" now carry lines like:

  src/ontology/mwo-edit.owl: 1 term changed on both sides, differently, out of 1 and 1. Each
  needs somebody to choose.
      Both sides relabelled Material, differently: this branch has "Material Entity", the other
      branch has "Material Thing".

It reports; it does not resolve. Which of two definitions of a class is right is not a tool's
decision, and there is still no three-way merge here to offer.

AGREEMENT IS REPORTED APART FROM DISAGREEMENT. Two people who made the SAME edit have not
conflicted, even though git says they have. Counting those as decisions would teach a curator to
skim the report, and the next one they skim will be real.


THE ESTIMATE'S PREMISE WAS WRONG, IN A USEFUL DIRECTION

Item 5 was listed as blocked behind items 6 and 7 - applicable diff objects, and a base version
per session - on the grounds that naming a disagreement needs a common ancestor and real change
objects rather than rendered strings.

For a GIT conflict git has kept a common ancestor all along: stage 1 IS the common version, and
no session, lock, vector clock or version counter was needed to obtain it. Rendered strings turn
out to be enough to NAME a disagreement; they are only insufficient to RESOLVE one. The thing
that genuinely needs a base version is the live collaboration path, which has none - and that is
item 7, still open.

A BUG THE MEASUREMENTS FOUND IN MY OWN FIRST VERSION

The first version inferred the shape of the conflict from which versions the OWL API could read:
no stage 2 meant "this branch deleted it". That is wrong exactly when git HAS the stage and it
will not parse - a file somebody committed with conflict markers still in it, which is the thing
docs/conflicts.md says happens today. It reported a broken file as a deletion, confidently, and
a user's next move after reading that would have been the wrong one.

Fixed by asking git which stages it kept (git ls-files -u) and reporting a parse failure as a
parse failure. Proven on a real repository with markers committed into stage 2, and guarded by
ConflictReviewTest.aStageThatWillNotParseIsNotReportedAsADeletion.

TWO MORE THINGS THE MEASUREMENTS CORRECTED:

  - The OWL API's Turtle parser is LENIENT. A file with a missing period and an undeclared prefix
    still parsed - into an ontology missing the class the broken line carried - so the report
    said "this branch removed Material", which is a true statement about the ontology that file
    actually describes. Genuinely unparseable stages are rarer than assumed; committed conflict
    markers are the realistic cause.
  - Delete/delete does not produce a DD status from a plain merge. GitRepo.isUnmerged admits DD,
    so the path is reachable and is covered, but it took a real merge to learn that the ordinary
    case never reaches it.


NINE DEFECTS AN ADVERSARIAL REVIEW FOUND IN THIS RELEASE, BEFORE IT SHIPPED

Four reviewers read the change along different dimensions and raised 16 findings; each was then
handed to refuters told to DISPROVE it. The ones below survived, were reproduced against real git
or measured directly, and are fixed here. The review cost about 2.5 million tokens across 30
agents and was worth it: eight of these were wrong output a user would have acted on.

1. A RENAME ON BOTH SIDES WAS REPORTED AS A DELETION. The one-sided branches tested for a missing
   stage 2 or 3 BEFORE asking whether git kept an ancestor. MEASURED on git 2.38.1: ours renames
   a.ttl to b.ttl, theirs to c.ttl, and the merge leaves `DD a.ttl`, `AU b.ttl`, `UA c.ttl` -
   single-stage sets. The report said "the other branch no longer has b.ttl" about a path that
   branch never had. A curator restoring it loses one of the two renames. Worse, it is the same
   confident lie that asking git for the stage list was added to prevent. No test could reach it:
   a single-stage set needs a null ancestor AND a null side, and no case passed both.

2. AN UNREACHABLE IMPORT MADE A READABLE FILE "UNPARSEABLE", IN 13.6 SECONDS. Each stage was
   loaded through a default-configured manager, which fetches owl:imports. MEASURED: an ontology
   importing two unreachable IRIs threw UnloadableImportException after 13.6s - per stage, three
   stages per file. An ODK edit file imports its modules by IRI, so this was the ordinary case,
   not a corner. The guarded configuration answers in 2.5s with the ontology intact, and nothing
   is lost because only each version's OWN axioms are compared.

3. TWO INDEPENDENT ADDITIONS OF ONE TERM WERE CALLED AGREEMENT. ReleaseDiff records an ADDED
   change with the term's rdfs:label as its only value, so two people who each introduced the
   same IRI with the same label were reported as agreeing while their definitions, parents and
   restrictions went uncompared.

4. A SECOND CHANGE TO A TERM COULD HIDE A DISAGREEMENT ABOUT IT. Only the last change per term
   was kept, so two sides that each relabelled Material differently AND moved it under the same
   parent reduced to one identical MOVED entry per side, compared equal, and were announced as
   agreement - with the label disagreement absent from the report altogether.

5. A CONFLICTED PATH WITH A SPACE IN IT GOT NO REPORT AT ALL. `git status --porcelain` quotes
   such a path - MEASURED: `UU "src/my ontology.owl"` - and the quotes were kept, so the path
   ended in `"` rather than `.owl`, the file was judged not an ontology, and nothing was said.
   Non-ASCII paths are octal-escaped per BYTE, so they are now gathered and decoded as the UTF-8
   they are rather than one escape at a time.

6. DURING A REBASE THE TWO SIDES WERE NAMED BACKWARDS. In a merge, stage 2 is this branch; in a
   rebase, cherry-pick or revert it is what is already on the new base and stage 3 is the change
   being replayed. MEASURED: during `git rebase` the status still prints UU and says nothing.
   Telling a curator their own edit is "the other branch" invites them to discard their own work.
   MERGE_HEAD is asked for once per report, and the sides are named neutrally when it is absent.

7. "NOTHING DISAGREES" WAS SAID ABOUT A FILE GIT HAD JUST REFUSED. MEASURED on a real conflict
   where both sides edited only the ontology's own rdfs:label: "Both sides changed 0 and 0 terms,
   and nothing they both touched disagrees" - while the commit was being refused, which invites
   the reader to conclude the refusal is a bug. The report now says plainly that it compares
   terms and not ontology-level annotations, comments or synonyms.

8. AN EMPTIED VERSION WAS CALLED UNREADABLE. git exits 0 with no output for an empty blob, which
   was read as a parse failure rather than as the empty ontology it is.

9. LinkageError escaped the soft-failure guarantee, which is the throwable this codebase
   documents as the realistic one when a class the host was expected to provide is absent.

WHAT THE REVIEW DID NOT COVER: the workflow verified at most four findings per dimension, so
three of the sixteen were never put to a refuter. Of the rest, four were judged house style or
cosmetic and are not fixed: the short-form duplication of ReleaseDiff.shortForm, MOVED agreement
compared on short parent names rather than IRIs, the indentation of collision lines surviving
OperationResult.note, and a weak assertion in gitFailingOutrightDoesNotThrow.

first written as a Java string literal, and Java reads `\\303` in source as an octal escape of

function that was measured to be correct. It builds its input from explicit characters now.

NON-VACUOUS BY CONSTRUCTION: the two deletion branches were swapped in the shipped code and
ConflictReviewTest.oneSideDeletingTheFileIsSaidOutLoud failed. Reverted and re-run green.

WHAT IS STILL NOT TRUE

  - Resolution is still last-writer-wins by arrival in the live path. No version check, no vector
    clocks, no three-way merge, no common ancestor anywhere in it.
  - Nothing can APPLY a decision. AxiomDiff and ReleaseDiff still return rendered strings rather
    than List<OWLOntologyChange>, so the report can name a disagreement and not settle one.
    docs/conflicts.md items 6 and 7.
  - The sender of a dropped operation is still not told; that needs a NACK the protocol lacks.
  - GitAction still has no test class of its own - no release has given it one. What it used to
    hold has moved into ConflictReview, which is covered; what is left in GitAction is the
    wiring, and it is exercised only by the host smoke starting without throwing.
  - Nobody has seen this report in a running Protege. It is measured through the shipped function
    against five real repositories, and the smoke proves the bundle starts - not that the dialog
    lays these lines out well.
  - Everything 1.125.0 listed as outstanding still is: no Zenodo DOI, no w3id PURL, not in
    Protege's plugin registry, the paper audited and not rewritten, .xlsx read-only, 39 thin
    patterns, no contact address or ORCID in CITATION.cff.
