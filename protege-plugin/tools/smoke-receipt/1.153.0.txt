WHAT THIS RELEASE ADDS

- New ODK project... writes ODK's own seed, every file byte for byte: the Makefile with all of
  ODK's targets, run.sh, the CI workflow in ODK's image, ODK's checks. Where Docker or Podman runs
  and ODK's image is on the machine, ODK's container writes it; otherwise OntoBoard renders ODK's
  own templates, which it carries. OntoBoard adds six files of its own.
- Build..., Release..., Refresh imports... and Update project files... run ODK's own targets, in
  one of three ways chosen in Check requirements...: with ODK's tools installed, in ODK's
  container, or by OntoBoard itself, which reads ODK's Makefile and runs its recipes inside
  Protege. Docker is not needed for a project of ODK's standard shape.
- A project's own Makefile and release script are respected. Rules of a project's own run in
  ODK's container; OntoBoard's own engine refuses them and says why.
- A release is ODK's release: make clean, then prepare_release, the files at the top of the
  project, the version IRI in ODK's shape or one of three others, the commit and the tag shown
  as git commands and run when you agree. Nothing is pushed.
- Stop stops ODK's container: OntoBoard names each container it starts and removes it when a run
  is stopped or out of time.
- A failed build says what stopped it - the reasoner's finding, the check and its terms, the
  quality report's errors, an OWL 2 DL violation - and Release says the same.
- A project made by 1.135 or before is carried over by OntoBoard > Project > Update project
  files...; until then Build and Release say so and change nothing.
- Check requirements... has a row for ODK's image and a button that pulls it when asked.
  OntoBoard never pulls by itself.
- The first term you make on the board asks which of ODK's two placeholder ID ranges is yours,
  and writes your name into it.
- The Assistant column: a cloud model with your own key, or a model on your own machine through
  Ollama. It answers questions about the selected term or the ontology, explains a reasoner
  problem and suggests changes as cards; nothing changes until Accept, and an accepted change is
  one Edit > Undo. docs/assistant.md says what is sent and where a key is kept.
- Proof on two ODK repositories, a materials-science application ontology and the mid-level
  ontology it builds on: the release files, and all import modules but one, are byte for byte
  what ODK's container makes when run directly; the one module differs in two comment lines.
- A review of the whole ODK work found seven defects that mattered and five smaller ones; all
  twelve are fixed, each with a test that failed first. docs/fixed.md has every one.


WHAT THIS RECEIPT DOES NOT COVER

- The scripted runs send mouse events to the components directly, so focus, hover, drag and the
  native file dialogs were not exercised with a real mouse on this jar.
- Linux and macOS: not run on this jar; CI runs the unit suite on Linux and on Windows.
- A real model: the assistant was checked with a connection that answers nothing. Its answers,
  with a cloud model or Ollama, are what the assistant's own benchmark is for.
- Pulling ODK's image from Check requirements...: never run on this machine, where the image was
  present. Podman: not tried.
- OntoBoard's own engine on a project with rules of its own: refused by design; such projects ran
  in ODK's container, as in the proof above. ODK's 79 sample configurations are held as seeds;
  which of their targets the engine runs is measured on nine projects, not on all 79.
- How long each task takes: docs/measurements.md has ODK in Docker against OntoBoard, task by
  task, five runs each way on this machine while other programs kept its processors 93% busy
  on average - every task agreed, and OntoBoard's slowest run was faster than ODK's fastest in
  each - but not a benchmark. The command that measures it on a quiet machine is beside it.
